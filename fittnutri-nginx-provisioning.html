CONTEXTO

Visão Geral da Arquitetura

O FittNutri é uma plataforma SaaS desenvolvida para nutricionistas gerenciarem pacientes, dietas e dados antropométricos. A infraestrutura foi provisionada em uma instância Amazon EC2 (Ubuntu 22.04), utilizando Docker Compose para orquestrar os serviços.

O Nginx atua como reverse proxy, sendo o único ponto de entrada da aplicação. Ele recebe todas as requisições externas nas portas 80 e 443, redireciona HTTP para HTTPS e encaminha o tráfego para os containers internos de frontend e backend.

Por que Nginx como reverse proxy? O Nginx permite que um único IP público sirva múltiplos serviços (frontend e API) via roteamento por path, além de centralizar a terminação SSL/TLS, rate limiting e headers de segurança em um único ponto de configuração.
ETAPA 1

Declaração do Serviço no Docker Compose

O primeiro passo foi declarar o container do Nginx no arquivo docker-compose.yml. O serviço utiliza a imagem oficial nginx:alpine, expõe as portas 80 (HTTP) e 443 (HTTPS), e monta três volumes bind para persistir a configuração e os certificados SSL fora do container.

docker-compose.yml — serviço nginx
nginx: image: nginx:alpine container_name: nginx restart: always ports: - "80:80" - "443:443" volumes: - ./nginx/conf.d:/etc/nginx/conf.d - ./nginx/certbot/www:/var/www/certbot - ./nginx/certbot/conf:/etc/letsencrypt depends_on: - frontend - backend networks: - fittnutri-network
DiretivaExplicação
image: nginx:alpineImagem oficial do Nginx baseada em Alpine Linux — leve (~23MB) e segura por padrão.
restart: alwaysO container reinicia automaticamente em caso de falha ou reboot da instância EC2.
ports: 80 / 443Expõe as portas HTTP e HTTPS na interface de rede pública da instância.
./nginx/conf.d:/etc/nginx/conf.dMonta o diretório local de configuração dentro do container, permitindo editar o virtual host sem rebuild.
./nginx/certbot/conf:/etc/letsencryptPersiste os certificados SSL emitidos pelo Let's Encrypt fora do container.
depends_on: frontend, backendGarante que o Nginx só sobe após os serviços que ele vai fazer proxy estarem disponíveis.
networks: fittnutri-networkColoca o Nginx na mesma rede Docker interna dos outros containers, permitindo resolução de nomes (frontend, backend).
ETAPA 2

Arquivo de Configuração do Virtual Host

O arquivo nginx/conf.d/fittnutri.conf é o coração da configuração do reverse proxy. Ele define dois blocos server: o primeiro escuta na porta 80 (HTTP) e redireciona tudo para HTTPS, o segundo escuta na porta 443 (HTTPS) e faz o proxy para frontend e backend.

lucas@ip-172-31-16-162:~/FittNutri$ cat ~/FittNutri/nginx/conf.d/fittnutri.conf
# Rate limiting: máximo 30 req/min por IP na API limit_req_zone $binary_remote_addr zone=api:10m rate=30r/m; server { listen 80; server_name fittnutri.duckdns.org; # Rota para validação do certificado Let's Encrypt location /.well-known/acme-challenge/ { root /var/www/certbot; } # Redireciona todo tráfego HTTP para HTTPS location / { return 301 https://$host$request_uri; } } server { listen 443 ssl; server_name fittnutri.duckdns.org; # Certificados SSL emitidos pelo Let's Encrypt via Certbot ssl_certificate /etc/letsencrypt/live/fittnutri.duckdns.org/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/fittnutri.duckdns.org/privkey.pem; ssl_protocols TLSv1.2 TLSv1.3; ssl_prefer_server_ciphers on; ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256: ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384; # --- Headers de Segurança HTTP --- add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always; add_header X-Content-Type-Options "nosniff" always; add_header X-Frame-Options "DENY" always; add_header Referrer-Policy "strict-origin-when-cross-origin" always; add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always; add_header Content-Security-Policy "default-src 'self'; ..." always; # FRONTEND — React via Vite location / { proxy_pass http://frontend:5173; proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; proxy_set_header Host $host; proxy_cache_bypass $http_upgrade; } # BACKEND API — Spring Boot location /api/ { limit_req zone=api burst=10 nodelay; proxy_pass http://backend:8080/; proxy_http_version 1.1; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; } }
Diretiva / BlocoFinalidade
limit_req_zoneDefine uma zona de rate limiting chamada "api" na memória compartilhada (10MB), limitando cada IP a 30 requisições por minuto na rota /api/.
listen 80 + return 301Captura todo tráfego HTTP e redireciona permanentemente para HTTPS, forçando conexões criptografadas.
acme-challenge/Rota especial usada pelo Certbot para validar a propriedade do domínio durante a emissão do certificado SSL.
ssl_protocols TLSv1.2 TLSv1.3Desabilita versões antigas e vulneráveis do TLS (1.0 e 1.1), aceitando apenas protocolos modernos e seguros.
ssl_ciphers ECDHE-*Suítes de cifra com Forward Secrecy — mesmo que a chave privada seja comprometida no futuro, sessões passadas permanecem seguras.
Strict-Transport-SecurityHeader HSTS: força o navegador a usar HTTPS por 1 ano (31536000 segundos), prevenindo ataques de downgrade.
X-Content-Type-Options: nosniffImpede que o browser "adivinhe" o tipo MIME de uma resposta, prevenindo ataques de MIME sniffing.
X-Frame-Options: DENYBloqueia a aplicação de ser embutida em iframes, prevenindo ataques de Clickjacking.
Content-Security-PolicyDefine quais origens podem carregar scripts, estilos e outros recursos, prevenindo XSS.
proxy_pass http://frontend:5173Encaminha requisições para "/" ao container "frontend" via rede Docker interna, sem expor a porta diretamente.
proxy_set_header Upgrade/ConnectionMantém suporte a WebSocket, necessário para o hot-reload do Vite em desenvolvimento.
proxy_pass http://backend:8080/Encaminha requisições para "/api/" ao container "backend", strippando o prefixo /api/ antes de repassar.
X-Forwarded-For / X-Real-IPRepassa o IP real do cliente para o backend, que de outra forma veria apenas o IP do Nginx.
limit_req zone=api burst=10Aplica o rate limiting definido: permite um burst de até 10 requisições simultâneas antes de recusar com HTTP 429.
ETAPA 3

Volumes Montados — Inspeção do Container

Após o container subir, é possível inspecionar os volumes bind-mount em execução para confirmar que os arquivos de configuração e certificados estão corretamente mapeados. O comando docker inspect retorna os metadados completos do container em formato JSON.

lucas@ip-172-31-16-162:~/FittNutri$
# Verificar os volumes mapeados para o container nginx $ docker inspect nginx --format='{{json .Mounts}}' | python3 -m json.tool [ { "Type": "bind", "Source": "/home/lucas/FittNutri/nginx/certbot/conf", "Destination": "/etc/letsencrypt", "Mode": "rw", "RW": true, "Propagation": "rprivate" }, { "Type": "bind", "Source": "/home/lucas/FittNutri/nginx/conf.d", "Destination": "/etc/nginx/conf.d", "Mode": "rw", "RW": true, "Propagation": "rprivate" }, { "Type": "bind", "Source": "/home/lucas/FittNutri/nginx/certbot/www", "Destination": "/var/www/certbot", "Mode": "rw", "RW": true, "Propagation": "rprivate" } ]
Source (host)Destination (container)Finalidade
nginx/certbot/conf/etc/letsencryptCertificados SSL emitidos pelo Certbot — persiste fora do container para sobreviver a recreações.
nginx/conf.d/etc/nginx/conf.dArquivo de virtual host — editável no host sem precisar fazer rebuild da imagem.
nginx/certbot/www/var/www/certbotWebroot usado pelo Certbot para o desafio ACME ao emitir/renovar certificados.
Por que usar bind mounts? Diferente de volumes Docker gerenciados, os bind mounts mapeiam diretórios reais do host. Isso permite que alterações na configuração do Nginx sejam aplicadas sem rebuild da imagem — basta editar o arquivo e executar docker exec nginx nginx -s reload.
ETAPA 4

Validação da Sintaxe e Portas Abertas

Antes de confirmar que o Nginx está funcionando corretamente, é necessário validar dois pontos: que a sintaxe do arquivo de configuração está correta e que as portas 80 e 443 estão efetivamente expostas na interface de rede pública.

lucas@ip-172-31-16-162:~/FittNutri$
# Testar sintaxe da configuração do nginx dentro do container $ docker exec nginx nginx -t nginx: the configuration file /etc/nginx/nginx.conf syntax is ok nginx: configuration file /etc/nginx/nginx.conf test is successful # Ver portas abertas pelo container nginx $ docker port nginx 80/tcp -> 0.0.0.0:80 80/tcp -> [::]:80 443/tcp -> 0.0.0.0:443 443/tcp -> [::]:443
VerificaçãoResultadoO que confirma
nginx -tsyntax is ok / test is successfulArquivo fittnutri.conf não possui erros de sintaxe e pode ser carregado pelo processo do Nginx sem falhas.
docker port nginx (80)0.0.0.0:80 e [::]:80Porta HTTP escutando em todas as interfaces IPv4 e IPv6 — acessível externamente.
docker port nginx (443)0.0.0.0:443 e [::]:443Porta HTTPS escutando em todas as interfaces — certificado SSL ativo e servindo tráfego criptografado.
Resultado final O Nginx está provisionado, configurado e em execução com sucesso. O tráfego externo chega na porta 443 (HTTPS), é encriptado com TLS 1.3, e roteado internamente via Docker network para os containers do frontend (React/Vite na :5173) e backend (Spring Boot na :8080), com rate limiting de 30 req/min por IP na rota /api/.
CONCLUSÃO

Resumo do Processo

O provisionamento do Nginx no FittNutri seguiu uma abordagem baseada em containers Docker, o que traz vantagens significativas em relação à instalação direta no sistema operacional: isolamento, portabilidade, versionamento da configuração junto ao código e facilidade de replicação em outros ambientes.

EtapaAção realizadaTecnologia
1 — DeclaraçãoServiço nginx definido no docker-compose.yml com volumes e dependênciasDocker Compose
2 — ConfiguraçãoVirtual host configurado com HTTP→HTTPS redirect, TLS 1.3, headers de segurança e proxy rulesNginx + Let's Encrypt
3 — VolumesBind mounts confirmados via docker inspect — configuração e certificados persistidos no hostDocker
4 — ValidaçãoSintaxe verificada com nginx -t e portas 80/443 confirmadas com docker portNginx + Docker
Considerações de segurança aplicadas A configuração implementa múltiplas camadas de segurança: TLS 1.2/1.3 com Forward Secrecy, HSTS, CSP, proteção contra Clickjacking (X-Frame-Options DENY), proteção contra MIME sniffing (X-Content-Type-Options nosniff) e rate limiting na API para prevenir ataques de força bruta e DDoS de aplicação.
